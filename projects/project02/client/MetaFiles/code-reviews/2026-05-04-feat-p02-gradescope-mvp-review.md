## Dimension findings

### 1. Functional completeness — Grade A-

The branch sets out to make the existing `api_*.js` files PDF-spec-conformant and ships that scope cleanly. Routes, response envelopes, status codes, body shapes, retry decoration on the spec-mandated MySQL paths, and the corresponding client adjustments all match the PDF on inspection. The grade is A- (not A) because two real spec-adjacent gaps remain: a 50% off-by-one on the user-facing path of `delete_images` if the S3 step throws unexpectedly, and a documents-don't-get-Rekognition policy that the PDF doesn't mandate. Neither is a Gradescope blocker; both are worth flagging.

Findings:
- ✨ All three route corrections (`POST /image` → `POST /image/:userid`, `GET /image/:assetid/labels` → `GET /image_labels/:assetid`, `GET /images/search?label=` → `GET /images_with_label/:label`) match the PDF — verified against the PDF spec at pages 13/17/18 and the client/server diff in `0aba589` — `projects/project02/server/app.js:111-120` (`0aba589`)
- ✨ The 400-not-404 conversion for `get_image` and `get_image_labels` correctly aligns with the PDF — pages 16, 18 prescribe 400 with `userid: -1` / empty `data: []` envelopes — `projects/project02/server/api_get_image.js:24,46` and `api_get_image_labels.js:24` (`d132696`)
- ✨ `post_image` body shape `{local_filename, data}` (no userid, since userid is now in URL) and `get_image` response key `local_filename` (was `localname`) both match PDF page 16 — `projects/project02/server/api_post_image.js:32` and `api_get_image.js:80` (`0aba589`, `d132696`)
- ✨ `delete_images` correctly uses `dbConn.query()` (not `execute()`) for the multi-statement `SET fk_checks=0; TRUNCATE labels; TRUNCATE assets; SET fk_checks=1; ALTER TABLE … AUTO_INCREMENT=1001` block per PDF page 19 — `projects/project02/server/api_delete_images.js:51-58` (`8045533`)
- ⚠️ `delete_images` orders DB-clear-then-S3-delete per PDF, but if the `DeleteObjectsCommand` throws *and* returns `s3response.Errors[]` non-empty, those per-key errors are silently dropped because the `try/catch` only catches throws. The lone caught path logs `s3err.message` but doesn't surface partial-failure metadata. PDF says "no negative effect since they have unique names" so this is tolerated, but it's worth a TODO — `projects/project02/server/api_delete_images.js:75-89` (`8045533`)
- 💡 Documents (non-photo extensions) skip Rekognition entirely (`kind === 'document'` short-circuits the `DetectLabelsCommand`). The PDF doesn't actually say to skip — it says Rekognition labels objects in "the image". This is a defensible reference-impl borrow (the lib does this), but the user wanting labels on a `.pdf` mistakenly named so by an extension twist will get an empty list silently. Worth a comment that it's a deliberate optimization, not the spec — `projects/project02/server/api_post_image.js:84-95` (`4959c2d`)
- 💡 The `is photo` set is hardcoded to `{.jpg, .jpeg, .png, .heic, .heif}`. Rekognition supports more (e.g., `.webp` since 2023). Edge-case-y; defer unless the autograder hits one — `projects/project02/server/api_post_image.js:21` (`4959c2d`)
- ⚠️ `get_image` does not handle the case where `s3response.Body` is undefined (S3 returned 200 with no body — rare but possible during eventual-consistency windows on very fresh uploads). The `for await (const chunk of s3response.Body)` will throw `TypeError: undefined is not iterable`. Wraps to a 500, so user-facing it's correct, but the error message is unhelpful — `projects/project02/server/api_get_image.js:67` (`d132696`)

### 2. Code elegance — Grade B+

The handler files read cleanly; comments are pragmatic and explain the *why* (PDF references, kind-derivation rationale, failure-tolerance rationale for S3-after-DB). Naming is consistent (`get_dbConn`, `validate_user`, `clear_db`, `collect_bucketkeys`). Two real issues bring this down from A: the per-route `dbConn` open/close pattern is duplicated across every handler (no pool), and the dynamic `import('p-retry')` boilerplate repeats six times.

Findings:
- ✨ Inner-function naming (`validate_user`, `insert_with_transaction`, `collect_bucketkeys`, `clear_db`, `try_get_labels`, `try_search`, `try_get_images`) consistently signals retry-wrappable units — readable at a glance — `projects/project02/server/api_post_image.js:46,107`; `api_delete_images.js:31,48`; `api_get_image.js:30`; `api_get_image_labels.js:17`; `api_get_images_with_label.js:21`

- ⚠️ Connection lifecycle pattern `let dbConn; try { dbConn = await get_dbConn(); ... } finally { try { await dbConn.end(); } catch(e) { /*ignore*/ } }` is duplicated across **every** handler — six handlers × two-or-three connection sites per handler — without a helper. The refactor cost is ~20 lines for a `withConnection(fn)` helper; the tax of NOT having it is paid every time someone reads a handler. Not refactor-now-blocking, but the next handler-touch should land it — `projects/project02/server/api_post_image.js:45-58,108-138`; `api_delete_images.js:31-43,48-65`; `api_get_image.js:30-44`; `api_get_image_labels.js:17-44`; `api_get_images_with_label.js:21-39` (across `4959c2d`, `8045533`, `d132696`, `0aba589`)
- ⚠️ The `const pRetry = (...args) => import('p-retry').then(({default: pRetry}) => pRetry(...args));` boilerplate appears **six times** across the JS files (the pre-existing `api_get_ping.js`, `api_get_users.js`, `api_get_images.js` plus the four files this branch changed). The 3x rule was triggered before this branch even started; this branch added three more occurrences without consolidating. A single `lib/p-retry-shim.js` module is ~3 lines — `projects/project02/server/api_post_image.js:18`, `api_delete_images.js:17`, `api_get_image.js:14`, `api_get_image_labels.js:9`, `api_get_images_with_label.js:8` (this branch) plus pre-existing files

Branch chose not to consume the lib — fine — but it could've at least lived in `helper.js` so other handlers could share it — `projects/project02/server/api_post_image.js:21-26` (`4959c2d`)
- 💡 In `api_post_image.js:54-58` the inner `validate_user` returns the rows array and the caller checks `.length === 0`. Returning a boolean (`async function user_exists(userid) { ... return rows.length > 0; }`) reads at-the-callsite without the rows-array detour. Minor — `projects/project02/server/api_post_image.js:46-58` (`4959c2d`)

### 4. Codebase alignment — Grade C

The branch deliberately ignores the post-Phase-0 architectural posture the codebase committed to. Phase 0 extracted `@mbai460/photoapp-server` into a workspace lib expressly so consumers stop duplicating service-layer code; **this branch duplicates service-layer code into the existing instructor-baseline files** — repository SQL, S3 / Rekognition orchestration, transaction handling, derive_kind logic, retry policy. The lib already exposes all of these correctly via `services.photoapp.{uploadImage, downloadImage, getImageLabels, searchImages, deleteAll}`. The choice is defensible *given the deadline* (PDF deadline was 2026-05-04 11:59pm CST and the work shipped at 09:14:33 CDT same day — six hours of head-room), but it leaves the codebase in a state where there are now **two parallel implementations** of the same use-cases for as long as the branch's structure persists. That's the situation Phase 0 explicitly built to prevent. Penalize the skip — not because the choice was wrong, but because the gaps it created are real and need surfacing.

Findings:
- ⚠️ The branch does not consume `@mbai460/photoapp-server` despite the lib being installed at the workspace root and ready (`lib/photoapp-server/README.md` § Consumers explicitly names `projects/project02/server/`). Every handler reimplements logic that already lives in `lib/photoapp-server/src/services/photoapp.js` — `projects/project02/server/package.json:11-19` (`60f760d`) shows direct deps on `mysql2`, `@aws-sdk/client-s3`, `@aws-sdk/client-rekognition`, `p-retry` instead of the lib export
- ⚠️ The bucketkey scheme in `api_post_image.js:75` is `uuidv4() + ext` (no username folder). The lib's `services.photoapp.uploadImage` uses the project-wide convention `${user.username}/${uuid.v4()}-${localFilename}` per `02-web-service.md:564`. This is a behavior divergence from Part 03's wire shape — if Phase 1 of Foundation later wires Project 02 to consume the lib, every uploaded asset's bucketkey shape changes mid-stream — `projects/project02/server/api_post_image.js:75` (`4959c2d`)
- ⚠️ No `mysql2.createPool` — every handler opens a fresh connection via `get_dbConn()` and calls `.end()` on it. The pre-existing `helper.js` baseline already does this, so the branch inherited the pattern, but the branch added three new handlers (`post_image`, `delete_images`, `get_image`) that compound the per-request connection cost. `01-foundation.md` Phase 7 mandates a pool — `projects/project02/server/helper.js:35-58` (pre-existing baseline) and the branch's three new connection sites in `api_post_image.js`, `api_delete_images.js` (`4959c2d`, `8045533`)
- 💡 The `pRetry` import boilerplate exists exactly because the codebase chose `p-retry@7.x` (ESM-only) in a CommonJS server. The lib has already paid this tax once via its services; consuming the lib would let this branch shed the boilerplate entirely. Architectural rather than cosmetic — `projects/project02/server/api_post_image.js:18` and the four other sites (`4959c2d`, `8045533`, `d132696`, `0aba589`)
- 💡 `app.use(express.json({ strict: false, limit: "50mb" }))` (pre-existing baseline at `app.js:30`) is the only boundary check. PDF agrees with 50MB cap, but the lib + `01-foundation.md` would add a `validate` middleware (zod-based) that would have caught e.g. missing `local_filename` *before* the route handler. Branch B's `if (data === undefined || local_filename === undefined)` body-shape check at `api_post_image.js:34` is a one-off — `projects/project02/server/api_post_image.js:34` (`0aba589`)
- ✨ Even though the branch chose not to consume the lib, several small details mirror lib conventions (`INSERT IGNORE` + `ROUND(?)` for label inserts; `kind` derivation; bounded `pRetry({retries: 2})`). The commit messages cite "matches the lib's pre-extraction Part 03 behavior" explicitly. Even when not consuming, the agent kept the lib's behavior contract visible — `projects/project02/server/api_post_image.js:124-128` (`4959c2d`)
